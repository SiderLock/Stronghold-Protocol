本轮优化服务器向玩家提供资源时的重复工作。战斗模拟、Bot 决策、房间人数与客户端画质规则没有改动。
过程与原始结果保存在本地 DEV-20261105-11。

## 计算预算与停顿诊断（2026-11-06）

程序的任务并发与计算时间片，不能等同于整个服务的 CPU / 内存配额。当前源码的主要边界如下：

| 路径 | 默认预算 | 作用范围 |
|---|---|---|
| 原版 AI 预演子进程池 | 可用 CPU 数减一，最多 2 个；每个子进程 old-space 512 MiB | 两核默认容量 1；预演与过大结果重算，见 [服主配置](../SERVER_SETTINGS.md#计算进程) |
| 主线程 Bot 准备与服务端普通战斗 | 每任务约 8 ms 的协作时间片 | 不是全房间合计预算；多个任务可叠加，单步不可抢占，战斗每 16 tick 检查时间 |
| 缓存路径的 HTTP 读取 / 压缩 | 两项并发许可 | 不限制房间、Bot 或整个进程的 CPU 使用；大文件流式响应另走原路径 |
| WebSocket 压缩 | 并发 4，level 6 | 压缩和发送完成回调仍可能排队；不等同于公网带宽预算 |

上游可选 `SP_WORKERS` 线程池与 `SP_REHEARSAL_WORKERS` 子进程池不同：前者未配置时关闭，
后者按 CPU 数选择默认容量。默认官方版本房间的普通 AI 战斗仍通过网络主进程的 `HeadlessJob` 分片；
其他官方版本及玩法插件房间由独立 match host 承载。排查时须关联房间版本与执行进程，
不能把默认版本的路径套到所有房间，也不能把预演移出主线程理解为所有战斗均已隔离。

整机平均 CPU 不高，仍可能出现主线程短时阻塞或发送队列积压；内存有余量也不能排除这两种延迟。
`[net] delivery delayed` 是带节流的诊断告警：`loopMs` 来自 250 ms 采样及最近 8 秒证据，
`maxSendMs` 是 `ws.send` 提交到完成回调的近期峰值或未完成时长，包含压缩、发送与回调调度。
它们不是完整的历史延迟分布、客户端 RTT，也不能单独证明公网出口已满。

进一步定位可在无对局的维护窗口启用现有 `SP_LOOP_SAMPLE=1`，结合阶段、回合、计算队列与发送耗时采样。
该设置需要重启；本次仅核对配置、日志与源码，没有调整线上参数或宣称卡顿已修复。

## 线上基线与定位

运行源码 `b33ce81d`，Node 22.23.3，2 个逻辑 CPU、约 3.5 GiB 内存。空闲时 Node RSS 约 383 MiB，
整机可用内存约 2.5 GiB，健康检查约 3 ms。cgroup 的内存记账还包含文件缓存，不能直接用它推断进程堆大小。

9,406,590 字节的官方特效索引超出原 8 MiB 压缩缓存阈值，每次响应重新执行流式 Brotli / gzip。
线上六次串行请求约 150～350 ms，较小的已缓存清单约 1～2 ms。源码同时存在先读文件、再等待压缩许可的路径，
多个不同文件可在排队期间保留原始缓冲区。

## 改动

- 复用现有压缩 LRU，把单文件缓存路径阈值调整为 16 MiB，使当前官方特效索引可共享并发任务和已压缩结果。
  总压缩缓存仍为 96 MiB，Brotli quality 5 / gzip level 6 保留。16 MiB 是本轮 `[ASSUMED]` 工程默认。
- 文件读取延后到取得现有压缩许可后执行。缓存路径最多两个活跃读取 / 压缩任务，读取失败也释放许可。
  两个 16 MiB 文件的活跃原始缓冲区预算为 32 MiB；这不是整个进程的内存上限。更大的文件继续使用流式响应。
- 缓存身份继续包含文件路径、大小、mtime、inode、ctime 和编码；Range、HEAD、304、内容哈希 URL 的处理保留。

## 同机隔离测量

在服务器上用相同 Node、相同真实索引、相同临时 HTTP 驱动比较部署代码和修改版。各编码七次请求，
首请求单独视为冷请求，其余六次取中位数；随后清空编码缓存，发起 20 个并发请求。测量进程使用低优先级，
有玩家接入即终止。临时服务只监听本机，未创建对局。

| 指标 | 原实现 | 修改版 |
|---|---:|---:|
| Brotli 热请求中位数 | 185.52 ms | 2.81 ms |
| gzip 热请求中位数 | 154.72 ms | 2.23 ms |
| 20 并发 Brotli 完成时间 | 2.40 s | 0.17 s |
| 20 并发阶段进程 CPU 时间 | 4.66 s | 0.17 s |
| 整个独立 HTTP 基准进程最高 RSS | 464 MiB | 160 MiB |

原始文件与两种编码的响应 SHA-256 在两版间完全一致。当前索引的两个压缩结果合计约 1.10 MiB，
由现有 96 MiB LRU 管理。峰值 RSS 包含临时请求发起端，不能当作正式游戏服务的内存降幅。
这些结果描述静态 HTTP 请求，尚未验证二十名真人整场对局、网络拥塞或其他服务器负载下的改善。

## 验证与应用边界

回归覆盖并发源读取准入、读取失败后的队列推进、大索引的并发去重与热缓存、Brotli / gzip 解码、
ETag / 304、Range 和超过新阈值的流式响应。还核验已有静态素材、时装和缓存目录行为。
宽范围静态界面检查保留既有的 CSS container 断言失败；本轮未修改该断言或其 CSS 输入。

应用此服务端修改需要在无正在进行或断线保留的对局时重启，先备份变更文件和安装清单。
本轮不修改游戏素材、玩家缓存目录版本或服务器私有配置。浏览器 build 标识仅反映客户端运行文件，
因此这一服务端优化可保持同一 build；运行源码以部署标记为准。公开状态见 [开发入口](README.md)。
