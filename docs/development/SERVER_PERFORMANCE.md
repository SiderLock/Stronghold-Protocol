服务没有额外的 CPU quota 或内存硬上限。下列判断依据实际进程环境、当前实现与固定负载；本轮保留全部现有配置，

| 开关 | 线上实际状态 | 建议与理由 |
|---|---|---|

| `SP_BOT_STRATEGY` | 未设，`legacy` | 暂不全服改为 `adaptive` / `ioleta-adaptive`。前者改变布阵搜索，后者还改变罗素采购；它们是 AI 策略选项，不能作为通用减负开关。 |

| `SP_BOT_REHEARSAL` | 未设，服务器预演 | 暂不全服改为 `host`。默认版本的 AI 队友预演交给房主浏览器 Worker，会增加房主设备负担；无可用房主、约 3 秒超时或错误仍回退。 |

### 自适应 AI 的固定负载对照

本机 Node 24.21.0，六真人保持手动、十四 AI，其中三个固定阿戈尔阵容；每席八枚棋子、基础三候选，
一个预热子进程，同一种子顺序运行。使用真实布阵 / 预演 / 应用结果流程，排除采购、网络和完整对局，
父进程 CPU 不包含子进程 CPU。以下为一次探索性样本，不代表生产吞吐、胜率或真人体验。

| 阶段 | 默认 AI / adaptive 整批耗时 | 默认 AI / adaptive 父进程 CPU | 默认 AI / adaptive 子进程任务 |
|---|---:|---:|---:|
| R10 普通轮 | 5.73 / 17.01 秒 | 2.36 / 11.30 秒 | 14 / 0 |
| R14 最终攻势 | 10.05 / 36.31 秒 | 1.77 / 21.98 秒 | 14 / 0 |

两者均在该场景的 125 / 195 秒备战时间内完成，真人未被自动准备、队列清空且无对局错误。
当前 `server/match/match/prep.js` 的默认子进程路径要求 `!job.limits`；自适应任务带搜索预算，因此这组任务在
主线程协作执行。任务数为 0 只表示没有进入该子进程池，不表示没有预演。
现有 `SP_WORKERS` 线程路径能携带预算；切换策略前，应独立核对隔离路径、峰值和实际对局表现。
另有兼容限制：当前 `SP_BOT_STRATEGY_SEATS` 只接受座位 `0–3`、最多四项，不能直接填二十席逐席列表。

### P2P 对延迟的边界

仅当主要瓶颈是服务器公共状态下行，且浏览器之间能稳定直连、有合适中继上行时，P2P 才可能改善这一部分延迟。
本项目增加浏览器转发的一跳，操作请求和回合运算仍依赖服务器。转发故障时的 WebSocket 看门狗约为 2.5 秒，
签名、补发和回退仍有成本；超过 60 KiB 的 P2P 帧也不能直接套用转发收益。
当前没有 STUN / TURN 配置，公网 NAT 穿透不能靠一个布尔值保证，TURN 又会引入中继流量。
参见 [本项目部署说明](../DEPLOY.md) 与 [MDN 的 ICE / STUN / TURN 说明](https://developer.mozilla.org/en-US/docs/Web/API/WebRTC_API/Protocols)。

对「全员操作或回合推进一起停顿」，优先关联事件循环、慢操作、计算队列和发送回调，再判断计算阻塞还是网络排队。
累计流量不能代替卡顿时段的峰值证据；总 CPU 未满也不能排除单段 JavaScript 阻塞，原理见
[Node.js 事件循环说明](https://nodejs.org/learn/asynchronous-work/dont-block-the-event-loop)。
带宽紧急冻结检测也继续保持关闭，未据本次调查改变门槛或开启自动冻结。

## 多 AI 计算调度与隔离（2026-11-06）

默认官方版本在客户端战斗模式下，把没有真人执行的普通 / 联防战斗接入现有预演子进程池，包括 AI、断线接管与过大结果重算。
进程数、512 MiB 子进程 old-space 上限、30 秒超时和 128 项等待队列保留；不另建一组计算进程。
首领与隐秘核心继续使用实时共享结算池，非默认版本 / 插件继续使用 match host。
失败、队列满或关闭时回退一次；结果与进度时间线回到父进程后仍按原战斗自然时间发布。
整批取消先完成当前取消栈，再启动剩余任务需要的替代子进程，避免连续启动即将被取消的进程。

每个进程的真实时间计算共享 `workQueue.js`，默认每轮约 8 ms、最多 64 个回调后让出事件循环；
使用 `setImmediate` 给 I/O 和普通定时器处理机会，避免额外依赖零毫秒定时器的最小等待时间。
这两个数是 `[ASSUMED]` 工程默认，单个操作不可抢占；不是 CPU 利用率上限或硬延迟保证。
Bot 准备、主线程战斗构造 / 分片、结果应用和复核经过计算队列，网络、心跳与普通截止时间不排入它。
普通 headless 工作每 4 tick 检查时间，测试日志保持每 16 tick 的兼容边界；虚拟调度与测试模式不切入新的计算队列。
冻结与销毁保留稳定句柄，取消一个房间不取消其他房间的工作。

慢操作日志区分同步处理耗时和异步总耗时，附当前房间版本、阶段 / 回合及计算队列；每 30 秒最多一条。
计算片达到 25 ms 时也有独立限频记录，包含排队等待时间。只记录受控上下文，不记录玩家身份、凭证或请求正文。
周期 `[loop]` 仍须 `SP_LOOP_SAMPLE=1`，补充版本、主线程队列及子进程队列；`workPeakEver` 是进程生命周期峰值。
这些信息只进入本地日志，不扩展 pong 或公开健康协议。参数说明见 [服主配置](../SERVER_SETTINGS.md#计算进程)。

## 计算预算与停顿诊断（2026-11-06）

以下记录优化前的诊断基线。任务并发与计算时间片不能等同于整个服务的 CPU / 内存配额；本轮修改后的路径见上节。

| 路径 | 默认预算 | 作用范围 |
|---|---|---|
| 原版 AI 预演子进程池 | 可用 CPU 数减一，最多 2 个；每个子进程 old-space 512 MiB | 两核默认容量 1；预演与过大结果重算，见 [服主配置](../SERVER_SETTINGS.md#计算进程) |
| 主线程 Bot 准备与服务端普通战斗 | 每任务约 8 ms 的协作时间片 | 不是全房间合计预算；多个任务可叠加，单步不可抢占，战斗每 16 tick 检查时间 |
| 缓存路径的 HTTP 读取 / 压缩 | 两项并发许可 | 不限制房间、Bot 或整个进程的 CPU 使用；大文件流式响应另走原路径 |
| WebSocket 压缩 | 并发 4，level 6 | 压缩和发送完成回调仍可能排队；不等同于公网带宽预算 |

上游可选 `SP_WORKERS` 线程池与 `SP_REHEARSAL_WORKERS` 子进程池不同：前者未配置时关闭，
后者按 CPU 数选择默认容量。默认官方版本房间的普通 AI 战斗仍通过网络主进程的 `HeadlessJob` 分片；
其他官方版本及玩法插件房间由独立 match host 承载。排查时须关联房间版本与执行进程，
不能把默认版本的路径套到所有房间，也不能把预演移出主线程理解为所有战斗均已隔离。

整机平均 CPU 不高，仍可能出现主线程短时阻塞或发送队列积压；内存有余量也不能排除这两种延迟。
`[net] delivery delayed` 是带节流的诊断告警：`loopMs` 来自 250 ms 采样及最近 8 秒证据，
`maxSendMs` 是 `ws.send` 提交到完成回调的近期峰值或未完成时长，包含压缩、发送与回调调度。
它们不是完整的历史延迟分布、客户端 RTT，也不能单独证明公网出口已满。

进一步定位可在无对局的维护窗口启用现有 `SP_LOOP_SAMPLE=1`，结合阶段、回合、计算队列与发送耗时采样。
该设置需要重启；当时仅核对配置、日志与源码，没有调整线上参数。后续本地实现也未替代线上真人验收。

## 线上基线与定位

运行源码 `b33ce81d`，Node 22.23.3，2 个逻辑 CPU、约 3.5 GiB 内存。空闲时 Node RSS 约 383 MiB，
整机可用内存约 2.5 GiB，健康检查约 3 ms。cgroup 的内存记账还包含文件缓存，不能直接用它推断进程堆大小。

9,406,590 字节的官方特效索引超出原 8 MiB 压缩缓存阈值，每次响应重新执行流式 Brotli / gzip。
线上六次串行请求约 150～350 ms，较小的已缓存清单约 1～2 ms。源码同时存在先读文件、再等待压缩许可的路径，
多个不同文件可在排队期间保留原始缓冲区。

## 改动

- 复用现有压缩 LRU，把单文件缓存路径阈值调整为 16 MiB，使当前官方特效索引可共享并发任务和已压缩结果。
  总压缩缓存仍为 96 MiB，Brotli quality 5 / gzip level 6 保留。16 MiB 是本轮 `[ASSUMED]` 工程默认。
- 文件读取延后到取得现有压缩许可后执行。缓存路径最多两个活跃读取 / 压缩任务，读取失败也释放许可。
  两个 16 MiB 文件的活跃原始缓冲区预算为 32 MiB；这不是整个进程的内存上限。更大的文件继续使用流式响应。
- 缓存身份继续包含文件路径、大小、mtime、inode、ctime 和编码；Range、HEAD、304、内容哈希 URL 的处理保留。

## 同机隔离测量

在服务器上用相同 Node、相同真实索引、相同临时 HTTP 驱动比较部署代码和修改版。各编码七次请求，
首请求单独视为冷请求，其余六次取中位数；随后清空编码缓存，发起 20 个并发请求。测量进程使用低优先级，
有玩家接入即终止。临时服务只监听本机，未创建对局。

| 指标 | 原实现 | 修改版 |
|---|---:|---:|
| Brotli 热请求中位数 | 185.52 ms | 2.81 ms |
| gzip 热请求中位数 | 154.72 ms | 2.23 ms |
| 20 并发 Brotli 完成时间 | 2.40 s | 0.17 s |
| 20 并发阶段进程 CPU 时间 | 4.66 s | 0.17 s |
| 整个独立 HTTP 基准进程最高 RSS | 464 MiB | 160 MiB |

原始文件与两种编码的响应 SHA-256 在两版间完全一致。当前索引的两个压缩结果合计约 1.10 MiB，
由现有 96 MiB LRU 管理。峰值 RSS 包含临时请求发起端，不能当作正式游戏服务的内存降幅。
这些结果描述静态 HTTP 请求，尚未验证二十名真人整场对局、网络拥塞或其他服务器负载下的改善。
