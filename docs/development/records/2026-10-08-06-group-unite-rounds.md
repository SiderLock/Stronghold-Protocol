## 需求、范围与验收

用户报告超多人房两轮联防可能不够，希望联防轮数上限等于固定组数，沿用原选人机制与其他结算规则。投票在讨论后确认：每个仍有后续轮可打的联防轮开放投票，每轮票数重置；通过后当前轮正常结束，跳过本回合后续全部联防，文案必须明确「后续全部联防」。投票真人资格和严格过半门槛不变。

- 开局一至五组对应至多一至五轮，每轮最多两名不同的完美作战队友，全回合最多十名；从全房依原逻辑选人，固定组数只提供轮数上限。
- 不因淘汰或退出重分组/重新按实时人数降低上限；候补失去资格时过滤，无敌人或无合格候补时提前结束。
- 保留各轮奖励、统计、敌人来源/属性/悬赏传递，按最后剩余敌人扣原漏怪玩家 LP。
- 投票不打断当前战斗、不提前启动新战斗，保留正常轮间收尾；新界面明确语义并检查较多席位和较小窗口。
- 只运行目标函数/第一回合状态机与必要 Edge 检查。父目录 AGENTS.md 新增要求：完整从头至第 14 回合测试先问用户，本次不做完整对局、完整测试或 golden。
- 按既有授权可进行本地功能提交，未授权远程操作或部署。不改项目外文件或上游 CHANGELOG。

## 调查与决定

| 问题 | 证据或来源 | 结论及确定程度 |
|---|---|---|
| 当前选人 | `helperOrder` | 源码确认：全房完美作战队友按部署数、有效羁绊、站立干员及座位排序，各对再比较层数；不是随机抽人。本次保留，已告知用户。 |
| 现有两轮边界 | `playerCapacity.js`、`unite.js` | 源码确认：八名存活者阈值、四名助手截断、下一轮清空候补、动态人数取消第二轮都要替换。 |
| 收益与 LP | `settle.js` | 源码确认：已按 history 加当前结果汇总收益，仅按最后敌人扣 LP，可承接多轮。 |
| 投票选择 | 用户异步答复 | 已确认：打完本轮后取消剩余全部联防，每轮重新投票，必须明确文案。 |
| 立即切轮风险 | `unitePhase.js`、`runner.js`、`lifecycle.js` | 源码推断：直接覆盖 fields 可能留下旧浏览器 authority；普通 forced 结束不记齐存活/未刷出敌人，不能直接用于跳轮。未做带宽测量。 |
| 正常网络流程 | `unitePhase.js`、`spec.js`、`messaging.js` | 源码确认：当前轮结果收齐后延迟收尾再启动下一轮；每轮 b.start 扇出完整 spec，漏怪越多报文可能越大。静态素材有缓存，不能推定每轮重下全部素材。更多轮会增加总启动次数，峰值与带宽影响尚未实测。 |

## 实现或操作

| 文件 / 函数 | 变化与理由 |
|---|---|
| `shared/playerCapacity.js` | 移除实时存活八人阈值，`uniteRoundLimit` 读取固定组数并限制 1–5，最多十名助手。 |
| `unite.js` | 按全房原排序保留至多组数×每轮人数的候补；计划保存独立 perRound 与实际 roundsMax（候选不足则缩短）。下一轮保留未用候补，按 playerId 排除已用/当前/退出/淘汰者；不再检查实时人数。每轮重置 skipVotes，skipRemaining 通过则不产生后续计划。 |
| `unitePhase.js` | 所有仍有后续计划和合格候补的轮次可投票；资格与门槛沿用原规则，锁定 skipRemaining；只在当前轮正常结束后结算。继续使用原 COMBAT_END 收尾，不新增即时中断或并发战场。 |
| `protocol.js`、`intents.js`、`gameActions.js` | 可选 voteId 贯通客户端与服务端，由 match 前缀、游戏回合、联防轮构成；新版 UI 始终携带，延迟旧轮请求拒绝。省略标识的旧请求仍兼容，因此旧客户端没有这项跨轮延迟保护。 |
| `hud.js`、英文翻译 | 顶栏显示 3/5 等当前/计划轮次，单轮保持原布局；按钮、标题、投过/通过状态和广播均明确「后续全部联防」，通过后的说明为「本轮结束后直接结算」。原塔图标、漏怪标签及队伍栏不改。 |
| `audit.js` | 对所有轮检查固定组预算、每轮最多两人、累计不重复和完美资格；资格判断与 planUnite 对齐。原漏怪来源中途离开时仍允许在后续轮归因，不因当前 alive 集合收窄误报。 |
| 目标测试及文档 | 更新旧两轮/八人取消断言，增加三至五轮、跨组、候补退出、剩余敌人传递、收益和末轮 LP、逐轮投票/旧轮保护/审计负例；D013 保留被替代 D006 的历史理由，开发流程的联防验证项同步为多轮。 |
