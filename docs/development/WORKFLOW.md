# 本地开发与记录流程

本流程用于我们的分支。每次任务的记录要让下一个维护者能回答：为什么改、改在哪里、依据是什么、如何验证、还缺什么。只记录有用的操作与结论，不保存整段聊天或大量工具输出。

## 1. 开始前核对

- 查看分支、HEAD 和工作区，区分用户已有改动与本次任务。不能从旧记录假定当前状态。
- 阅读 [本目录入口](README.md)、相关 [决定](DECISIONS.md) 和最近的 [任务记录](records/README.md)，再读关联源码。
- 明确需求、验收条件、影响范围与当前授权。涉及规则取舍时先提出选项；已覆盖当前动作的授权无需重复询问。
- 从 [模板](templates/record.md) 新建任务记录，先写需求、基线、计划和状态。恢复被中断的同一任务时继续原记录。

## 2. 记录怎么命名、怎么分

使用 `records/YYYY-MM-DD-NN-short-topic.md`，任务编号为 `DEV-YYYYMMDD-NN`。日期按 Asia/Shanghai 的任务开始日期，`NN` 为当天递增序号；主题用小写英文与连字符。

一个明确需求或一次上游合并对应一篇记录，可以包含多个功能提交。新需求另建记录；独立的后续修正另建记录并链接前一篇。短调查同样记录，但不为每条命令单独创建文件。

状态使用：`计划中`、`进行中`、`已完成`、`暂缓`、`待复现`、`已取消`。状态描述要说明是实现完成还是仅调查完成；待复现的报告不能记成已修复。

## 3. 实现时保留哪些信息

- **需求与决定**：用户最终确认的口径，特别是人数、阈值、掉线/托管、淘汰、回滚等边界。长期决定写入 `DECISIONS.md`，任务记录引用其编号。
- **实现与理由**：主要文件和函数、前后行为、选择此做法的原因；放弃的方案只有在会影响后续判断时才保留。
- **证据**：提交、源码位置、测试、明确来源的规则资料，以及用户报告。区分「用户观察」「当前源码」「测试结果」「推断」「尚未确认」。
- **验证与限制**：实际运行的命令、结果、环境、跳过项与原因；不把计划写成已执行，也不把单机 AI 流程写成真人联机压测。
- **遗留与下一步**：可执行的下一步、当前阻碍、关联待办编号和接手入口。

原始日志、截图和下载文件通常留在项目的忽略缓存中；记录必须保存足够的关键结论和复现步骤，不能只链接随时可能消失的 `.cache` 文件。确需长期保留的小型证据可放本目录的 `records/evidence/` 并使用相对链接；不提交素材包、浏览器配置、依赖、密钥或私人连接信息。

## 4. 按影响范围验证

优先运行与修改有关的测试和必要检查。只有新增改动、失败或未解决风险需要扩大覆盖时，才扩大或重复测试；不默认每次运行完整 `npm test` 和 golden。

| 修改内容 | 选择验证的方向 |
|---|---|
| 只有文档 | Markdown 相对链接、引用文件、记录索引、Git 差异范围；不需要启动对局 |
| 房间人数、协议索引 | 容量边界、协议校验、房间与客户端同步 |
| 卡池、跨组赠送 | 分组边界、副本归还、信标接收组及满池情况 |
| 策略/机变轮选 | 真人优先、超时、跳过、托管、断线和重连 |
| 联防/投票 | 固定组数上限与多轮推进、候补资格和不重复、逐轮投票门槛、打完本轮后取消后续全部并结算 |
| 共享战斗、领袖血量 | 服务端与浏览器一致性、限伤边界、按需复核 golden |
| 界面布局 | 实际浏览器、目标分辨率、较多席位、状态图标及交互 |
| 上游合并 | 先按上游差异和本地冲突点选择，再决定是否扩大到完整回归 |

截至 2026-10-08，用户指定浏览器测试使用 **Edge**。后续以用户更新的要求为准。记录浏览器、分辨率和场景；无头界面检查、对局状态机测试与真实多人游玩分别描述。

## 5. 完成时一起更新

1. 在任务记录补充最终实现、实际验证、未解决项及提交归属。
2. 向 [记录索引](records/README.md) 加入这一任务；相关决定改变时更新其状态或新增决定，不悄悄覆盖旧理由。
3. 更新 [入口](README.md) 中发生变化的基线和待办。规则文档以链接为主；需要改已有上游文档时单独说明理由与范围。
4. 核对差异和新增文件是否都在授权范围内；按当前授权进行本地提交。没有推送授权时由用户手动推送。
5. 向用户报告结果、验证、遗留问题、本地提交及实际远程/部署状态。

本地开发记录写在本目录。发布摘要、上游 CHANGELOG 和逐次开发记录职责不同；不因写本地记录而自动改动根目录的 `CHANGELOG.md` 或 `change.md`。

## 6. Git 提交格式

本分支后续普通提交采用 `type(scope): 简短结果`。类型与范围用小写英文，摘要可用中文或英文，写清具体行为。历史提交保留原样，不为统一格式重写已共享历史。

| 类型 | 用途 |
|---|---|
| `feat` | 新功能或新的玩法能力 |
| `fix` | 已确认问题的修复 |
| `docs` | 文档和记录 |
| `test` | 测试或基准变更 |
| `refactor` | 保持行为的代码整理 |
| `chore` | 依赖、工具、打包等维护 |
| `perf` | 有测量依据的性能改进 |

范围按主要模块，例如 `capacity`、`draft`、`unite`、`boss`、`ui`、`development`。一次提交解决一个可解释的问题；关联代码、测试与任务记录可以一起提交。避免把无关修复、批量格式化、下载素材混入同一提交。

复杂修改的正文写明问题与前后行为、关键理由、实际验证及记录路径。调查未复现时不使用修复摘要；基准变化必须说明为什么预期输出应改变。

```text
fix(unite): 修正托管切换后的投票门槛

说明触发条件、修改后的行为和关键边界。

验证：列出实际运行的检查及结果。
记录：docs/development/records/YYYY-MM-DD-NN-topic.md
```

**避免提交哈希循环**：已有代码提交可以直接写哈希；记录和代码同一提交时，填写「与本文同一提交」并在提交正文引用记录路径，用 `git log -- <记录路径>` 查询归属。不为把提交自身哈希写回而反复追加提交或 amend。

上游合并可使用清晰的合并摘要，如 `Merge upstream vX.Y.Z into feat/IncreasePlayerCapacity`，正文记录真实来源提交、冲突取舍、验证和对应记录。是否创建本地提交、拉取或推送仍取决于当前会话授权，文档格式本身不授予操作权限。

## 7. 公开整合边界

本地过程记录、模板和原始测量留在忽略目录。公共入口只保留维护结论与可公开依据，不新增对私人文件的链接。合并时同时检查目标分支新增的提交对象与最终目录；普通删除不能抹掉历史对象。存在私人过程提交时，按 [同步流程](UPSTREAM.md) 使用净化整合提交。已有共享历史不改写、推送不使用 force；推送和部署分别遵循用户授权。
